# Multi-Document Intelligence Workbench

60-minute AI engineer assessment project for a **banking** document-review workflow. A user uploads synthetic application and supporting files (PDF, CSV, TXT), enters an analysis instruction, and receives structured findings with document provenance.

Built with **React**, **Node.js**, **TypeScript**, and **MySQL**. Database name: `multi_doc`.

This project was developed with **Cursor** (Grok 4.6). Architectural choices below were made by the candidate and encoded in `.cursor/rules`.

## Architecture

```
frontend/   React + Vite UI (upload, instruction, results, copy)
backend/    Express API, extractors, analysis provider, MySQL
shared/     API and domain TypeScript contracts
samples/    Synthetic documents only — no real customer data
```

Pipeline:

1. Validate files (count, size, extension, MIME).
2. Extract each document independently (PDF / CSV / TXT).
3. Run per-document fact extraction.
4. Run collective comparison without merging documents into one unstructured prompt.
5. Persist analysis metadata and structured JSON. Original file bytes are not stored.

The analysis layer is an `AnalysisProvider` interface. Default: deterministic **mock**. Set `AI_PROVIDER=openai` and `OPENAI_API_KEY` to swap in an LLM later.

## Setup

### Prerequisites

- Node.js 20+
- MySQL 8 listening on port 3306
- Copy environment file (do not commit `.env`):

```powershell
copy .env.example .env
```

Edit `.env` if your MySQL user/password are not `root` / empty.

### Database

You do **not** need to run SQL by hand. On backend start the API:

- creates database `multi_doc` if it is missing
- creates `analyses` and `documents` tables if they are missing

Optional explicit bootstrap:

```powershell
cd backend
npm install
npm run setup:db
```

Reference schema (already applied by the app): `backend/src/db/schema.sql`.

### Backend

```powershell
cd backend
npm install
npm run samples
npm test
npm run dev
```

API: `http://localhost:3001`  
Health: `GET http://localhost:3001/api/v1/health`

### Frontend

```powershell
cd frontend
npm install
npm run dev
```

UI: `http://localhost:5173`  
Vite proxies `/api` to the backend.

## Completed functionality

- Multiple-file upload with PDF/CSV/TXT allowlist, size/count limits, MIME + extension checks
- Custom analysis instruction (treated as untrusted input)
- Independent then collective analysis with document boundaries preserved
- Results: summary, comparison table, discrepancies, missing-information report, key-value extraction, independent per-document analysis
- Source document on every finding; facts vs AI interpretation labelled
- Copyable generated output
- Per-document statuses for unsupported, unreadable, empty, invalid, and failed files
- MySQL persistence of analysis JSON and document metadata (not full file content)
- Automated tests for backend pipeline/API validation and frontend results rendering

## Assumptions

- A single demo/workbench user header (`x-user-id`, default `demo-user`) is sufficient for this assessment; not a full identity platform.
- In-memory processing of uploads (max 5 × 2 MB) is safer than writing user filenames to disk.
- Heuristic/mock extraction is acceptable when no LLM key is provided; the provider interface is the production seam.
- Sample companies, names, licences, and revenue figures are fictional.

## Known limitations

- Mock extraction depends on labelled fields (`Company name:`, `Revenue:`, CSV `field,value` rows). Unstructured prose will yield fewer facts.
- Image OCR is out of scope (PDF/CSV/TXT only).
- Rate limiting is in-process (not Redis).
- No background job queue; analysis runs in the request.
- Optional OpenAI path is implemented but not required.

## Security considerations

- API keys and DB credentials stay on the backend.
- Parameterized MySQL queries; user-scoped analysis reads (`id` + `user_id`).
- CORS allowlist, payload limits, upload allowlist, generic error responses.
- User instruction and document text are untrusted; injection-like instruction language is ignored by the mock.
- No real banking/customer documents. Financial values in samples are synthetic and never rewritten.
- Full document text is not stored in MySQL.

## How this would be productionised

- Replace the demo user header with real authn/z (SSO, per-case access).
- Swap `mockAnalysisProvider` for a production LLM via `AnalysisProvider`.
- Object storage with server-side encryption, malware scanning, and retention/deletion jobs.
- Durable rate limiting, structured audit logs, HTTPS only, secret manager for credentials.
- Human-in-the-loop review before any credit decision; never auto-approve from model output.

## Personally made decisions

- Keep the 60-minute scope: no RAG, vector DB, Docker, Kubernetes, or Redis.
- Store structured results + metadata only, not original bytes.
- Deterministic mock as default so the workbench runs without an LLM vendor.
- Shared TypeScript types as the API contract between frontend and backend.
